Solita tener un problema con la estructura de mi proyecto, ya que usaba los components de forma gloabl y mezclava los componentes reutilizables con especificos de páginas, por lo que, terminaba teniendo una especie de "dumping ground". Por lo que, opte por usar un enfoque: Feature-Based / Domain-Driven Structure, es decir, organiza por features (módulos funcionales), no por tipo de archivo.

Principios clave que seguí:

- Colocación por proximidad: Si algo solo se usa en una feature → vive dentro de esa feature.
    Ejemplo:
        Hero.tsx → features/landing/components/
        NO en components global.

- Shared ≠ Default: Solo va a shared si cumple:
    - Reutilizable en múltiples features
    - No contiene lógica de negocio específica

    Ejemplo:
        Button → shared
        AuthForm → feature auth

- Services por dominio

    Evita:
        services/
        AuthService.ts
        UserService.ts

    Mejor:
        features/auth/services/auth.service.ts
        features/admin/services/user.service.ts

- Routing modular
    Cada feature define sus rutas:

    // features/auth/routes.ts
        export const authRoutes = [...]

        Luego agregas en un agregador:

        // core/router/routes.ts
        import { authRoutes } from '@/features/auth/routes'
        import { adminRoutes } from '@/features/admin/routes'

        export const routes = [
        ...authRoutes,
        ...adminRoutes
        ]

- Separación de responsabilidades
    pages → composición (UI + hooks)
    components → piezas UI
    hooks → lógica reutilizable
    services → IO / API
    types → contratos

- Cada uno como feature independiente → bajo acoplamiento.

- Algo imporntate es de no sobreingenierizar con:
    Clean Architecture completa
    Carpetas como application/, domain/, infrastructure/
    Eso solo es útil si el sistema crece demasiado.

Regla práctica final
- Si eliminar una feature no rompe otras → tu arquitectura está bien.
